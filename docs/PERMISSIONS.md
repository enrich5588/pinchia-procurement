# 部門與個人權限管理

系統管理員（啟用中的 `User.is_superuser`）登入後，可從側欄「權限管理」或 `/permissions/` 設定。此頁分為「部門權限」與「個人權限」，顯示目前設定、實際生效結果、來源與異動紀錄。一般員工與部門主管無法修改權限；除下述預設公司管理員外，此管理身分須由既有管理程序人工指定。

## 生效順序

Django 管理後台（`/admin/`）亦限制啟用中的超級使用者，單獨具有 `is_staff` 或模型維護權限不會開放此入口。

各業務模組另受 [面板開放狀態](PANELS.md) 控制：未開放時，一般同仁即使取得個人或部門授權仍不能進入；系統管理員可驗證開發中的模組。面板開放後才依以下個人／部門規則判斷。

清單每頁顯示 20 筆，提供上一頁、下一頁與頁碼。翻頁及儲存權限會保留搜尋、部門與帳號狀態篩選，以及選取的對象；重新搜尋或改選部門時從第一頁開始。頁首顯示篩選後的總筆數及本頁資料範圍。

部門與個人頁籤直接顯示完整清單；點選項目後載入權限編輯區。部門可依名稱搜尋；人員可依姓名、帳號、M365 登入名稱、信箱及部門搜尋。清單標示 M365／本機帳號、停用狀態與明確設定數量，搜尋與切換目標不會儲存權限；需按「儲存權限設定」才會套用。手機版先顯示清單，選取後跳至編輯區。

公司預設系統管理員為 `tonychi@pin-chia.com`。設定由 `M365_DEFAULT_ADMIN_UPN` 控制，預設為此帳號；公司租用戶驗證成功、Graph 身分一致且為成員帳號時，依 Graph `userPrincipalName` 精確比對（忽略大小寫）授予 staff 與 superuser。不依 `mail` 或未綁定的本機帳號名稱授權。設為空值可停用自動授權，但不會自動撤銷既有管理員；停用帳號仍不能登入。

每個權限可設定「繼承」「允許」「拒絕」：

1. 有個人明確設定時，以個人設定為準。
2. 個人選擇繼承時，讀取其目前所屬部門的明確設定。
3. 部門也選擇繼承時，使用系統預設。

例如資訊部允許財產管理，小王個人設定拒絕，則只有小王無法管理；將小王改回繼承，就恢復部門權限。個人明確允許亦可覆寫部門拒絕。部門由 M365 登入時的 Graph `user.department` 同步；異動部門後，適用新部門設定，原有個人設定仍保留。

未登入或停用帳號不具權限。啟用中的超級使用者具有全部權限，不受拒絕設定影響，以免鎖住管理入口。變更於下一次請求生效，不必重新登入；已完成的操作不會回溯取消。

## 權限項目

| 功能 | 進入權限 | 處理／管理權限 | 一般使用者預設 |
| --- | --- | --- | --- |
| 辦公用品 | `supplies.access` | `supplies.manage` | 可進入、無處理權 |
| 設備申請 | `equipment.access` | `equipment.manage` | 可進入、無處理權 |
| 財產清冊 | `assets.access` | `assets.manage` | 可進入、無管理權 |
| 資產登記 | `registrations.access` | `registrations.manage` | 可進入、無審核權 |
| 協作案件 | `collaboration.access` | `collaboration.manage` | 可進入、無統籌權 |
| 數位簽呈 | `approvals.access` | `approvals.view_all`（全公司閱覽） | 可進入、無全公司閱覽權 |
| 資料庫監看 | `database.monitor` | 系統管理員專用，無寫入功能 | 拒絕且不可委派 |

共 13 項，各模組獨立設定。處理、管理及全公司閱覽必須同時允許該模組的進入權限。「系統管理」整個區塊（資料庫監看、權限管理、面板管理）僅啟用中的 `is_superuser` 帳號可見與使用；`is_staff`、管理部門身分及部門／個人允許規則皆無法越過此限制。資料庫監看設定在權限頁中為停用欄位，歷史 `database.monitor` 規則保留但不再授權一般帳號。直接輸入網址或送出 POST 同樣會拒絕。

進入權限保留原有資料範圍：用品、設備與登記以本人案件為主；財產清冊以本部門為主；協作限收件部門；簽呈限申請人或可參與簽核的人員。處理或管理權限可擴大至對應模組的全公司案件。既有案件狀態、本人修改、指定簽核人及承接部門等操作限制仍會檢查；全公司閱覽不代表可代替他人簽核。

拒絕進入會同時隱藏導覽、首頁相關資料與操作入口，直接輸入網址或送出 POST 也會由後端拒絕。既有 `FEATURE_OPEN_TO_ALL=false` 的功能閘門仍優先限制一般使用者，不能透過個人授權開啟未放行功能。

## 正式部門與升級

正式名稱為 **管理與事業發展部**。本次 migration 的處理方式：

- 若只有舊名稱「管理部」，保留同一筆部門主鍵改為正式名稱，因此既有人員及業務外鍵保留。
- 若正式名稱已存在，使用正式部門；若兩個名稱同時存在，不自動合併人員與資料，避免錯誤轉移。
- 正式部門預設授予用品處理、設備處理、財產管理、登記審核及協作統籌，不自動授予簽呈全公司閱覽。早期 migration 曾建立的資料庫監看規則已不具授權效果。
- 之後新建相同正式名稱的部門，初始化上述五項。部門一般儲存不會重新授權，管理員移除的權限不會自行恢復。僅有舊簡稱的新部門不會自動取得管理權。

升級後可在部門權限頁調整這些預設授權。若兩個名稱同時存在，請先核對 Graph 回傳值及人員歸屬，再依公司組織維護程序整理。

## 儲存與稽核

設定只允許 POST 並驗證 CSRF，規則與異動紀錄於同一交易寫入。每次有異動時記錄操作者、目標、時間與各權限前後值，頁面顯示該目標最近 20 筆；管理後台可唯讀查閱紀錄。兩人先後編輯同一份設定時，舊版本送出會提示重新載入，避免覆蓋他人修改。

規則儲存在 `PermissionRule`，紀錄儲存在 `PermissionAudit`；選擇繼承會移除該層的明確規則。程式維護時應透過 `organization.permission_service.save_permissions` 儲存，以保留交易、版本檢查與紀錄；直接改資料庫不會自動產生紀錄。
