# 品嘉系統人員權限設計(摘要版,供練習/移植對齊)

> 這是**規則摘要**,不是正式 repo 源碼。你的實作對齊這份語意,
> 之後把概念移植回主系統時就是機械工作。

## 三層身分

| 身分 | 判準 | 說明 |
|---|---|---|
| 管理員 | `User.is_superuser` | **永遠人工勾選**,不由程式自動授予;全站唯一的「未上線功能可見」身分 |
| 部門主管 | `UserProfile.is_manager` | 約 37 位;有部門歸屬才算數(無部門=旗標無效,fail closed) |
| 一般同仁 | 登入即是 | |

## ⚠️ 血淚紅字:主管 ≠ 管理員

`is_manager` 與 `is_superuser` 是**兩條完全不相交的線**。主管與一般同仁在
「功能可見性」上受同一條規則管;管理員才是例外。正式系統在員工通訊錄頁
把這兩個混過一次,修了一輪。你的每一個權限判斷都要問:這裡要的是「主管」
還是「管理員」?寫錯的症狀是安靜的(頁面照開),只有測試抓得到——
所以**每個閘門都要有三身分測試**(admin 可/主管不可/同仁不可 各一條)。

## 功能上線閘門(feature gate)

- 一個功能=一筆註冊(key/status/release/urls);「同仁可用」=
  `released AND (complete OR alpha_release)`。
- 未放行:側欄無入口**且**直接打網址 403 —— 「只藏入口不擋網址等於沒擋」。
- 閘門在 middleware 一處攔路由,不在每支 view 掛裝飾器(漏一個的症狀是安靜的)。
- 你的 stub 已有同型 `can_use_feature`,沿用。

## 簽呈簽核的身分擴充

簽呈引入第四種身分:**簽核角色(ApprovalRole)**——「總經理」「財務主管」等
是角色不是人,人透過 ApprovalRoleMember 掛進角色(可多人,取當時有效者)。
簽核權判定永遠問角色,不問個人;人事異動改成員表,單據不動。
