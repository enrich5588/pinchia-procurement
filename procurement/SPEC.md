# 辦公用品採購 — 功能規格(現行行為)

> 這是主平台上這個功能**目前的行為**。你的任務:在本骨架中把它完整實作出來,
> 並依 §7 的改善方向擴充。看不懂的先問,不要猜 —— 規格有疑義以 AI 資訊部答覆為準。

## 1. 核心概念:「一張單大家一起填」

不是一人一張申請單。流程仿紙本傳閱單:

```
管理部開單(收單中) → 各部門同仁各自加自己要的品項列
→ 管理部收單(已收單,不再接受新增) → 管理部標記已採購
→ 東西到了,各同仁自己登入逐列點「我已領取」(簽收)
```

## 2. 角色與權限

- **管理部同仁**:開單、收單、標記已採購
- **任何登入同仁**:在「收單中」的單子上新增自己的品項列;對自己的列簽收
- 不能替別人簽收;不能動別人的列
- (整合後另有功能上線閘門,由平台處理,你用 stub 的 feature_required 模擬)

## 3. 狀態機(鐵律)

`open → closed → purchased`,**只能往前**。任何倒退操作要擋下並給訊息。
狀態順序只定義一次(model 的 ORDER),view/樣板都問它,不得各寫一份。

## 4. 編號慣例

紀錄編號格式:`OS-<民國年>-<四碼流水>`(例 OS-115-0001),全公司唯一。
併發下不得重號 —— 想想兩個人同時開單會發生什麼,寫測試證明你擋住了。

## 5. 刻意不做的事(別畫蛇添足)

- **不做核准鏈**:公司另有簽呈系統,這裡的狀態是收單進度不是核決。
- **不做品項字典/庫存**:自由文字品項即可。

## 6. 現行欄位參考(自己設計完再來對照)

表頭 SupplyRequest:record_no/company(公司別)/filled_on(開單日)/
due_on(收單截止,可空=不設截止)/department(承辦單位,可空)/status/
created_by/created_at/legacy_note(舊格式單備註)

品項列 SupplyRequestItem:request(FK)/item_name/quantity/unit/note/
requester(FK User,誰要的)/department(該列的部門)/received(已領取)/
received_at/added_at

## 7. 練習的擴充方向(依序)

1. 把 §1-§6 完整做出來+測試
2. 收單截止日到期自動關單(management command,適合排程)
3. 每張單的品項彙總檢視(採購的人要印得出來)
